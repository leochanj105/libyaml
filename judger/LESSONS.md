# Lessons from Building an Independent Judger for a Math Library

## Context

We built a bitwise-exact differential test suite to judge the correctness of
Rust transpilations of a C math library (libmcs). The judger compiles the same
test inputs against the C library and the Rust library independently, runs both,
and compares outputs bit-for-bit.

## 1. Use established test suites, don't invent your own

We sourced tests from two well-known projects:

- **glibc libm-test** — the GNU C Library's math test vectors, covering special
  values (NaN, ±inf, ±0, denormals, overflow/underflow boundaries).
- **core-math worst cases** — INRIA's research database of inputs that are
  hardest to round correctly for each math function.

These are complementary: glibc tests edge-case *behavior* (what happens at NaN?),
core-math tests rounding *precision* (does the last bit round correctly?). Neither
alone is sufficient.

**Lesson:** Don't write test inputs by hand. Decades of research have produced
curated test data for math libraries. Use it.

## 2. The original test data supports more than you think

glibc's `auto-libm-test-in` and `libm-test-*.inc` files are designed to be
compiled for all precisions (float, double, long double) by swapping a type
header. We initially only generated double tests and missed all float coverage.
The same data, cast to float, tests the float functions — exactly as glibc
intends.

**Lesson:** Read how the upstream project uses its own test data before
extracting a subset. You may be leaving coverage on the table.

## 3. Separate data from code for large test sets

Core-math has ~16 million worst-case inputs. Our first approach baked them into
C source files as printf statements. GCC used 36GB of RAM trying to compile a
2.2-million-line `main()` and never finished.

The fix: store inputs as plain text data files, write a small C driver that reads
from stdin, calls the function, and prints the result. Compile once, pipe data
through. 16M tests run in 13 seconds.

**Lesson:** If your test data is large, don't embed it in source code. Use a
data-driven approach: small driver + external data files.

## 4. Fault isolation is essential for differential testing

When testing a potentially buggy library, one crash kills all remaining tests.
We implemented per-test fault isolation using:

- `sigsetjmp`/`siglongjmp` to set a recovery checkpoint before each test
- Signal handlers for SIGSEGV, SIGFPE, SIGBUS, SIGABRT to catch crashes
- `alarm()` to catch infinite loops (the Rust exp2 had hangs on boundary inputs)
- `write()` instead of `fprintf()` in signal handlers (async-signal-safe)

A crashed test prints `= FAULT` to stdout (keeping output lines 1:1 for diffing)
and logs details to stderr. Execution continues with the next test.

**Lesson:** Any test that calls into untrusted code needs fault isolation.
Signal handlers + longjmp handle 99% of cases. The per-test alarm adds overhead
(~1s per hang) so make it configurable.

## 5. Always rebuild before testing

We initially tested pre-built binaries and got dramatically wrong results.
Source files had been edited but binaries weren't rebuilt. After `cargo build
--release` on all targets, the numbers changed completely:

| Version | Before rebuild | After rebuild |
|---------|---------------|---------------|
| S3 WC divergences | 403,974 | 21,246 |
| S5 WC divergences | 406,028 | 6,904 |

**Lesson:** Never trust a pre-built binary. Rebuild from source immediately
before testing, every time. Stale binaries invalidate entire experiments.

## 6. Branch coverage doesn't predict correctness for math libraries

We measured LLVM branch coverage of the test suite: 90.1% of library branches.
The scenarios with higher branch coverage in their *own* test suites didn't
necessarily produce fewer divergences in the judger.

The reason: most math library bugs are not in control flow. They're in
computation — wrong constants, wrong parenthesization, wrong operator precedence.
Two inputs can take the exact same code path but produce different rounding
results due to floating-point non-associativity.

Example: `val_lo + (y2 - w) + val_hi` vs `val_lo + ((y2 - w) + val_hi)`.
Same branches taken, different result due to addition order. One extra pair of
parentheses fixed 14,342 worst-case divergences in log10.

**Lesson:** For math libraries, branch coverage is necessary but nowhere near
sufficient. Value-sensitivity testing (core-math worst cases) catches bugs
that branch-coverage-guided testing misses entirely.

## 7. One input can matter more than a million

Across five fix scenarios (S1-S5), four produced nearly identical results
(~22,000 divergences). S5 had 7,716 — a 3x improvement. The entire difference
came from one test input: `log10(5.0)`.

This input, generated by an LLM test generator as a "reasonable coverage value,"
happened to expose a parenthesization bug in log10's final accumulation step.
The AI fixer corrected it. No other scenario's test generator picked `5.0` for
log10 — they picked `10.0`, `1e300`, `DBL_DENORM` instead, which don't trigger
the rounding sensitivity.

**Lesson:** Test input diversity matters more than test volume. A single
well-placed input can be worth more than millions of poorly-placed ones.
This is why curated test suites (glibc, core-math) are valuable — they
represent decades of researchers finding exactly such inputs.

## 8. The judger must be independent from the system under test

Our judger uses glibc and core-math test data, not the test suites generated
by the fix scenarios themselves. Each scenario generates tests, fixes bugs
until its own tests pass, then the judger evaluates with completely different
inputs.

This matters: a scenario can achieve 100% on its own tests while still having
thousands of bugs. Every scenario passed all its own tests. The judger found
7,700 to 22,100 remaining divergences depending on the scenario.

**Lesson:** The test suite used for judging must be independent from the test
suite used for development/fixing. Otherwise you're measuring how well the
system fits its training data, not how correct it actually is.

## 9. Systematic test data beats clever test generation

The core-math worst-case files are not "clever" — they're the output of
exhaustive mathematical searches for hard-to-round inputs. They don't target
specific code paths or branches. They just enumerate inputs where the exact
mathematical result falls close to a rounding boundary.

This brute-force approach found 21,246 divergences that none of the five
AI-generated test suites caught. The AI test generators produced ~2,000 tests
each with high branch coverage. Core-math's 16M inputs with zero branch
awareness found 10x more bugs.

**Lesson:** For numerical correctness, systematic mathematical enumeration
beats heuristic test generation. Branch coverage guides you to code paths;
worst-case enumeration guides you to values that stress the computation itself.
